# 技术栈总结 · 个人部署记录

> 本文记录本项目一次真实的端到端部署所用的技术栈与工程取舍,供个人复盘与分享。
> **不含**任何公网 IP、API Key、管理员账号等敏感信息;部署时请从环境变量/控制台读取这些值。

## 一、系统分层

| 层 | 选型(本次真实部署) | 说明 |
|---|---|---|
| 基础设施 | 云主机(纯 CPU,8 核 16G,Ubuntu 22.04) | 实时计费,用时才开;systemd 配开机自启 |
| 容器 | Docker + Docker Compose | Dify 与检索服务各一套 compose |
| 智能体平台 | **Dify**(开源,自托管) | Chatbot(知识问答)与 Agent(知识 + 工具)两种应用 |
| 大模型 | **Qwen3.7-Plus**(对话)、**GLM-Embedding-3**(向量) | 经 OpenAI 兼容接口接入(本次用学校 MaaS 平台的免费额度);可替换为任意 OpenAI 兼容服务 |
| 知识库 / RAG | Dify 知识库 + 多语言 Embedding | 24 份文献平台指南(16 订阅库 + 8 公开平台),覆盖 11+ 语区 |
| 实时检索工具 | 自建 **litsearch** 微服务(Python + FastAPI + uvicorn) | **多源聚合检索**:OpenAlex + Crossref + Semantic Scholar;依次查询并按 DOI/标题去重、按被引排序 |
| 工具接入 | OpenAPI/Swagger → Dify 自定义工具 | Agent 以 ReAct 模式调用 |
| 代码/数据 | GitHub(开源,MIT) | 知识库、工具、部署套件、人设统一版本管理 |

## 二、请求流程

```
用户 → Dify 应用(Qwen3.7-Plus)
   ├─ 意图=“去哪找” → 检索知识库(多语言向量)→ 平台路线图 + 检索技巧 + 术语词包(带引用)
   └─ 意图=“要具体论文” → 调 litsearch 工具 → OpenAlex/Crossref/Semantic Scholar → 论文列表(标题/作者/年份/开放获取链接)
→ 模型综合为中文可执行回答
```

## 三、工程中解决的几个真实问题

1. **容器 TLS 握手超时**:Docker 默认 MTU(1500)大于云网络可用值,TLS 握手大包被丢导致容器内连不上外部 API。解决:把 Docker 的 MTU 调成与宿主机网卡一致(`daemon.json` 的 `default-network-opts`)。
2. **国内拉取失败**:`get.docker.com`、GitHub、Docker Hub 常被重置。解决:apt 装 Docker、Docker 镜像加速、Git 走代理/镜像克隆。
3. **平台封禁 80/443/8080**:Dify 对外端口改用 `8443`,并在 Dify 的 `.env` 里把对外 URL 配成带端口,使分享链接正确。
4. **模型工具调用**:部分模型经兼容接口不支持原生 function calling(会把工具调用写成文本)。解决:Agent 用 **ReAct** 模式,或改用工具调用更规范的模型(本次用 Qwen3.7-Plus)。
5. **Crossref 相关度排序**:其相关度排序值为 `score` 而非 `relevance`,误传会 400。解决:相关度检索省略 `sort`(用默认),仅按被引/时间排序时显式传参。
6. **Semantic Scholar 限流**:无 API Key 时 429 频繁。解决:有限重试 + 建议配置 `S2_API_KEY`;任一源失败不影响其它源。

## 四、现状与边界(诚实表述)

- **多源聚合检索能力**已跑通:OpenAlex 稳定;Crossref 排序参数已修正;Semantic Scholar 无 key 时受限流,建议配 key。当前为**依次查询**聚合,非并发。
- **通用化改造已完成**:知识库访问链接已去除机构身份参数(`u=`、`accountid=` 等);仍保留对平台本身的客观描述。
- **尚缺系统化评测(Benchmark)**:见 `eval/` 的评测框架与黄金问题模板,用于量化意图路由、工具调用成功率、文献真实性/链接有效率、引用准确率、诚实降级率、响应时间、任务完成率。
